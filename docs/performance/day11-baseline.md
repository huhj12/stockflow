# DAY 11 성능 기준 측정

## 목적과 결론

기존 30종목 검색·정렬·관심종목 구현을 변경하지 않고 반복 가능한 성능 기준을 마련했다. 실제 검색의 입력→결과 프레임 중앙값은 308.7ms이며 기존 275ms debounce를 포함한다. 서버 요청과 JSON 처리 중앙값은 로컬에서 1.5ms였다. 이 조건에서 검색 전체 시간을 서버 지연으로 해석할 수 없다.

합성 3,000행 정렬은 기본 CPU에서 중앙값 732.2ms, CPU 4배 제한에서 4,553.3ms였다. 전체 DOM 요소 수는 33,063개다. 따라서 다음 DAY에는 가상 스크롤의 접근성과 복잡성을 검토하고, 도입 전후 같은 시나리오를 비교한다. 이번 변경에는 가상 스크롤·memo·상태 관리 변경 등 성능 최적화가 없다.

## 환경과 데이터

- 측정 날짜: 2026-11-23. 측정 대상 구현 커밋: db3fd07b644b1ab05063fd06afc513e6a297e568. 최종 원본 JSON의 sourceCommit과 trackedWorktreeDirty=false를 확인한다.
- Windows 11 10.0.26200, Intel Core i5-9400F 2.90GHz, 논리 CPU 6개, Node.js 24.22.1, Chromium 156.0.8078.4, headless 1280×800.
- Next.js production --profile 빌드와 React Profiler 경계 사용. 개발 서버·Strict Mode 수치를 사용하지 않는다. profiling 자체의 오버헤드는 포함된다.
- API localhost:4100, 웹 localhost:3100에서 순차 실행. 기존 Docker 3000·4000 서버는 측정 중 유지했다. 최종 실행 중 lint·typecheck·빌드 등 별도 검사를 병행하지 않았다. OS와 다른 앱의 부하를 완전히 통제한 실험은 아니다.
- 실제 API는 기존 30종목 그대로다. 합성 30·300·3,000행은 브라우저 요청 가로채기로만 주입하며 API·Mock 카탈로그는 늘리지 않았다. 900000부터 시작하는 테스트 코드와 성능테스트 이름을 사용하며 해당 종목의 상세·시세는 제공하지 않는다.
- CPU 4배는 Chrome CDP의 실행 속도 제한이며 실제 모바일 기기나 특정 하드웨어의 성능을 뜻하지 않는다. 네트워크 제한은 없고 합성 데이터는 실제 서버를 거치지 않는다.

## 측정 방법

시나리오마다 워밍업 2회 후 유효 샘플 7회를 기록했다. 실제 검색은 매번 페이지를 다시 열어 TanStack Query 캐시를 초기화하고 005930을 검색한다. 합성 검색은 고유 검색어로 캐시 재사용을 피하되 모든 행을 반환해 결과 재생성 비용을 측정한다. 정렬은 가격 오름차순·내림차순을 교대하고, 관심종목은 동일 코드의 저장 상태를 교대한다. localStorage는 측정 전용 브라우저 context에 격리한다.

- 이벤트→프레임: 브라우저 캡처 단계에서 input 또는 click 이벤트 시각을 기록한다. MutationObserver로 기대 행 수·첫 코드·정렬 방향 또는 관심종목 상태를 확인하고 requestAnimationFrame 두 번 뒤 종료한다. Playwright의 locator 탐색·자동 스크롤 전 시간은 포함하지 않는다. 실제 픽셀의 paint 완료를 직접 추적한 값은 아니며 UI 반영 후 프레임 기회까지의 근사값이다.
- API: Node fetch와 JSON 파싱을 함께 잰 왕복 시간이다. 서버 내부 처리 시간이나 인터넷 지연을 뜻하지 않는다. 브라우저 Resource Timing의 API duration은 원본 raw.apiMs에 별도 기록한다.
- React: stock-dashboard Profiler 경계가 보고한 actualDuration을 작업 중 commit별로 합산한다. baseDuration, phase, startTime, commitTime도 원본에 보관한다. React 렌더 작업 시간이며 DOM commit·스타일·레이아웃·paint 비용과 같지 않다.
- DOM: 결과 반영 후 문서 전체 요소 수다. 행 수와 혼동하지 않는다.
- 긴 작업: 해당 측정 구간과 겹친 Long Tasks API 항목 수다. 표의 값은 7회 합계이며 INP·TBT·Lighthouse 점수가 아니다. 관찰자 비용도 있으므로 production 무계측 결과와 직접 비교하지 않는다.
- p50·p95: nearest-rank 방식. 7개 샘플의 p95는 최댓값이다. 통계적 신뢰 구간·운영 SLA를 제시하지 않는다. 여러 실행의 결과를 합치지 않고 최종 단독 실행만 기록했다.

## 렌더링 해석과 다음 검증

검색에서는 샘플별 Profiler commit 3회, 정렬과 관심종목 토글에서는 각 1회가 관찰됐다. 검색의 로딩·쿼리 변경·결과 반영 같은 상태 전환을 고려해야 하므로 commit 수만으로 불필요한 렌더링이라고 판단하지 않는다. 관심종목의 React 작업은 동일 크기 전체 정렬보다 작았으며, 이번 경계 계측만으로 개별 컴포넌트 함수 호출 수를 증명하지는 않는다. 부모/행별 호출 추적이 필요하면 별도 DevTools trace로 확인한다.

3,000행의 이벤트→프레임 시간은 React actualDuration보다 훨씬 크다. 큰 DOM의 commit·브라우저 렌더링 비용을 추가 추적할 근거지만 이 차이를 전부 레이아웃 비용이라고 단정할 수 없다. 다음 DAY에서 DOM 수를 제한하는 방식과 정렬·키보드·접근성 유지 방식을 비교하고, 같은 원본/시나리오/CPU 조건으로 전후 측정한다. 30종목 MVP에 성급하게 캐시·memo·가상화를 적용하지 않는다.

## 재현

Node.js 24에서 저장소 루트에서 실행한다. 3100·4100 포트가 사용 중이면 기존 서버를 종료하지 않고 실패한다. 설치된 Chromium을 사용하며 Windows의 기존 .tools 브라우저 경로는 필요할 때만 설정한다.

```shell
npm ci
npx playwright install chromium
npm run bench:build
npm run bench:stocks
```

기본 7회 샘플이며 BENCH_SAMPLES를 5~30 정수로 설정할 수 있다. 결과는 .tools/performance/day11-baseline.json에 기록한다. 이 문서와 함께 보관한 [최종 원본 JSON](day11-baseline.json)은 자동 덮어쓰기하지 않는다. 새 기준은 측정 환경과 코드 변경을 확인한 뒤 명시적으로 갱신한다. 스크립트는 자신이 기동한 측정 서버와 브라우저를 종료하며 기존 Docker 서버는 건드리지 않는다.

bench:build는 .next를 profiling 설정으로 다시 빌드하므로 일반 서비스 실행이나 E2E 전에 NEXT_PUBLIC_ENABLE_PROFILING과 NEXT_PUBLIC_API_BASE_URL을 해제하고 npm run build로 일반 산출물을 복구한다. 일반 npm run build에는 profiling 플래그가 없고 Profiler 경계를 마운트하지 않는다. 성능 수치를 CI 성공/실패 임곗값으로 사용하지 않는다. CI는 기존 기능 회귀와 품질 검사만 유지한다.

## 기능 회귀 검증

측정 후 일반 npm run build로 profiling 플래그와 측정 API 주소가 없는 산출물을 복구했다. format:check, lint, typecheck, Vitest 34개, production build, Playwright E2E 23개가 모두 통과했다. E2E 동안만 기존 StockFlow Docker 컨테이너를 중지하고 테스트 종료 후 재기동했다. 측정용 3100·4100 서버는 스크립트 종료 시 정리했다.
