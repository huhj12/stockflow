# DAY 12 대량 종목 목록 가상화와 전후 비교

## 결과

같은 계측 스크립트로 기존 표와 가상 표를 각각 측정했다. 합성 3,000행 정렬의 이벤트→프레임 중앙값은 기본 CPU에서 933.1ms → 27.8ms, CPU 4배 제한에서 2,951.3ms → 26.4ms였다. 해당 정렬 구간 전체 DOM은 33,063개 → 221개, 계측된 마운트 행은 3,000개 → 13~14개로 줄었다. 가상 목록의 중간 스크롤이나 포커스 고정 상황에서는 행 수가 달라지며 E2E에서는 50개 미만을 확인했다.

실제 30종목 검색은 311.9ms → 312.2ms로 큰 차이가 없었다. 100개 이하 목록은 기존 전체 표를 유지하므로 작은 목록의 개선율을 주장하지 않는다. 검색 시간에는 기존 275ms debounce가 포함된다. 정렬 배열과 전체 데이터는 메모리에 유지하며 네트워크 최적화나 서버 페이지네이션을 추가하지 않았다.

이 결과는 한 PC의 합성 데이터 실험이며 운영 SLA·실제 모바일 성능·모든 사용자 상황의 개선율을 뜻하지 않는다. 낮은 지연 구간에서 4배 CPU 결과가 기본 CPU보다 작은 경우는 프레임 기회·타이머 해상도·샘플 변동을 고려해야 하며 더 느린 CPU가 더 빠르다는 뜻이 아니다.

## 구현 결정

- apps/web에만 @tanstack/react-virtual 3.14.28을 추가했다. 기존 Query·Zustand·StockListItem 계약을 재사용하고 서버 Mock 30종목은 변경하지 않았다.
- 100개를 초과할 때만 가상화한다. 이 값은 소규모 MVP를 유지하기 위한 초기 정책이며 최적 임계값이라고 측정한 값은 아니다. 전체 목록 표시 버튼으로 일반 표로 전환할 수 있고 검색·필터 변경에도 이 선택은 유지한다.
- 네이티브 table·thead·tbody·tr·th 구조를 유지한다. 행 높이는 72px로 추정하고 실제 tr을 ResizeObserver 기반 measureElement로 측정한다. 글자 확대·헤더 크기 변경도 관찰한다.
- 가상 표에는 고정 열 너비와 fixed table layout을 적용해 가시 행 교체 때 열 너비가 흔들리지 않게 했다. 이 보고서는 가상화·표 레이아웃·포커스 처리 전체 변경의 전후 비교이며 가상화 엔진만의 기여도를 분리한 실험은 아니다.
- 헤더 높이를 virtualizer 시작 여백과 스크롤 여백에 반영하고 sticky header를 사용한다. spacer tr은 aria-hidden 처리하며 논리 행 수와 aria-rowindex를 제공한다.
- 포커스가 있는 코드는 현재 화면 밖으로 스크롤돼도 rangeExtractor로 유지한다. 고정 행과 가시 범위가 떨어져 있을 수 있어 각 행 사이의 간격을 별도로 계산한다.
- 방향키·Home/End·PageUp/PageDown으로 링크 또는 관심종목 버튼 사이를 이동한다. Tab/Shift+Tab은 인접한 논리 행을 연결하며 양 끝에서는 목록 밖으로 빠져나간다. 행이 마운트된 뒤 포커스를 적용하고 가로 방향도 화면에 드러나게 한다.
- 정렬은 전체 rows에 적용한 뒤 가시 범위를 선택한다. 정렬과 새 검색 결과는 스크롤을 맨 위에서 시작한다. 이번 변경에서 정렬 memo나 서버 검색 계약을 바꾸지 않았다.
- TanStack Virtual의 가변 인스턴스 메서드는 React Compiler 자동 memoization과 호환되지 않으므로 이 컴포넌트만 use no memo 경계로 두었다. 해당 hook 위치에만 이유를 명시한 lint 예외를 적용했으며, 라이브러리 호환성이 개선되면 재검토한다. virtualizer를 외부의 memoized 컴포넌트에 전달하지 않는다.

- 변경 전 구현 커밋: 572ca89e590641f68fa8287695f4a7e9508d5732. 변경 후 최종 구현 커밋: 30fad7f71a8a62188a640b34da960b4ed701f924. 양쪽 원본의 trackedWorktreeDirty는 false다.
- Next production --profile 빌드, 기본 CPU와 CDP 4배 CPU 제한, 워밍업 2회 뒤 샘플 7회. 순차 단독 실행했으며 같은 API·데이터·행 수·정렬 순서를 사용했다. 다른 OS 앱의 부하는 완전히 통제하지 않았다.
- 실제 API는 30종목, 합성 30·300·3,000행은 브라우저 요청 가로채기로만 주입했다. 합성 종목은 실제 상세·시세를 제공하지 않는다.
- DAY 11 계측에 논리 행 수/실제 마운트 행 구분과 출력 라벨을 추가한 뒤 기존 구현부터 다시 측정했다. 관심종목은 동일한 코드 900000을 선택하며 가상화에서 필요한 스크롤은 클릭 타이머 시작 전에 수행한다. 과거 DAY 11 수치를 가져와 개선율로 사용하지 않았다.
- 이벤트 캡처부터 기대 DOM 상태 확인 후 requestAnimationFrame 두 번까지 측정했다. 실제 픽셀 paint를 직접 추적한 값은 아니다. React actualDuration은 Profiler 기록을 합산한 별도 값이며 두 값의 차이를 전부 레이아웃 비용으로 단정하지 않는다.
- p50·p95는 nearest-rank이며 샘플 7개의 p95는 최댓값이다. 긴 작업은 측정 구간과 겹친 Long Tasks API 항목의 7회 합계다. INP·TBT 점수는 아니다.
- [변경 전 원본](day12-before.json), [변경 후 원본](day12-after.json)에 모든 유효 샘플, React commit, 긴 작업, 환경을 보관했다. 이 문서에는 최종 비교 실행만 사용했다.

## 재현

각 구현 커밋의 깨끗한 체크아웃에서 의존성과 Chromium을 설치하고 실행한다. 기존 Docker 3000·4000 서버와 별개인 3100·4100 포트가 비어 있어야 한다. 같은 PC·브라우저·화면 크기·샘플 조건을 유지한다.

PowerShell에서 변경 전에는 BENCH_LABEL을 day12-before, 변경 후에는 day12-after로 설정한다.

```powershell
npm ci
npx playwright install chromium
$env:BENCH_LABEL = 'day12-after'
# 이 PC에 이미 설치된 브라우저를 사용할 때만 지정한다.
$env:PLAYWRIGHT_BROWSERS_PATH = Join-Path $PWD '.tools/browsers'
npm run bench:build
npm run bench:stocks
```

결과는 .tools/performance/<BENCH_LABEL>.json이다. .tools는 Git에서 제외하며 검토한 최종 결과만 docs/performance에 보관한다. 측정 후 일반 npm run build로 profiling 빌드와 측정 API 주소를 복구한다. 현재 CI에서는 성능 수치를 임곗값으로 검사하지 않고 기존 기능 회귀를 검증한다.

## 검증과 남은 범위

기존 기능별 E2E를 유지하고 대량 목록 시나리오 5개를 추가했다. 포커스 고정·방향키·Home/End·Tab 경계 이탈·가로 방향 노출·전체 데이터 정렬·상세 진입·전체 목록 읽기·글자 확대·모바일 폭·시장 필터·검색 복귀를 검증한다.

자동 검증은 Chromium이다. NVDA/VoiceOver 등 실제 스크린리더와 Safari·Firefox 조합은 별도 수동 검증이 필요하다. 전체 목록 표시 대안을 제공하지만 모든 보조 기술의 동작을 보장하지 않는다. 초고속 연속 스크롤의 프레임 드롭, touch 기기, 새 데이터가 실시간 삽입되는 목록, 서버 페이지네이션은 이번 범위가 아니다.
